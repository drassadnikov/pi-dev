Правила формирования тест-кейсов для импорта в PPTM (pptm-core, POST /app/testing/api/v1/test-issues, файлы test-cases-*.json): 1) Один шаг = бэк + фронт: `action` — бэкенд-запрос (сервис/метод/топик, заголовки, тело, внутренняя цепочка сервисов) + название экрана из «Экраны.md»; `expectedResult` — HTTP-статус, тело ответа, проверка БД + картинка экрана (base64 `<img>` из o:\Obsidian\img), соответствующая бэкенд-ответу. 2) Литеральный `\n` в тексте шагов запрещён (в PPTM виден как два символа "\n") — использовать `<br>`; в f-строках генераторов не писать `\\n`. 3) Каждый кейс должен быть меньше ~256 КБ (иначе HTTP 500 от sfera-vtb-audit-adapter: 413 Payload Too Large): картинки сжимать до 480px / JPEG quality 45, дублирующие «пустые» экраны в одном кейсе не дублировать; после генерации проверять max-размер кейса по JSON. 4) HTTP 401 при импорте — проблема токена на стороне импортера, не данных: переимпортировать со свежим токеном. 5) preConditions/steps — массив объектов {action, expectedResult}, строки в массиве вызывают HTTP 500. 6) В описаниях (description) и шагах тест-кейсов не указывать ссылки на файлы-источники (напр. «(Экраны.md)») — в PPTM эта информация не несёт пользы; номера экранов (напр. «Экраны — 4.2.1») указывать можно. 7) Формат предусловий (preConditions) и шагов (steps) в PPTM: служебные метки «Шаг (Винительный падеж):» и «Ожидаемый результат (Именительный падеж):» в тексте НЕ писать. `action` в предусловиях — «N. <действие, imperative>» (номер ОБЫЧНЫМ шрифтом); в шагах — «<b>N.</b> <b><заголовок шага, imperative></b>» (номер шага ЖИРНЫМ) + бэк-часть (вызов/заголовки/тело/внутренняя цепочка) + название экрана Яндекса. `expectedResult` — в предусловиях состояние после подготовки (именительный падеж), в шагах **жирное** (<b>…</b>) краткое резюме результата (1-2 предложения, именительный падеж) + HTTP-статус, тело ответа, проверка БД + картинка экрана. Фразы «Подготовить условие тестирования» и «Условие выполнено, окружение готово» не использовать.
8) Дополнительные атрибуты (additionalAttributes) тест-кейсов в JSON для PPTM: ключ `technology` всегда "API" (все кейсы — интеграционные API-тесты); ключ `direction` выставлять по названию кейса: "Негативный сценарий" → direction="Негативный", "Позитивный сценарий" → direction="Позитивный", "Интеграционный сценарий" → technology="API", direction="Позитивный".
